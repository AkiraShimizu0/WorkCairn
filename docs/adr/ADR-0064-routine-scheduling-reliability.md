# ADR-0064: Routine Scheduling Reliability / Reconciliation

## Status

Accepted

## Context

ADR-0063 (PHASE U-4) connected an Active Routine to a self-sustaining chain of Scheduler occurrences, but its own Final Report flagged one unclosed correctness risk before Internal Core is considered done: `ExecuteRoutineActivate` commits the Routine's Inactive→Active transition, then separately creates the first next-occurrence Schedule. If the second step fails — Schedule Plan preflight rejection, a transient Vault I/O error, a crash between the two steps — the Routine is left durably **Active with no future occurrence**. This is a Continuity violation: an unattended-automation primitive whose entire purpose is "keep producing Planning requests on a cadence" silently stops doing that, with no durable signal distinguishing it from a healthy Active Routine, until a Human happens to notice.

**Failure-window reconstruction**, confirmed directly from `internal/process/routine_plan.go` and `internal/process/command_ledger.go` as they stood at `d8945dd`:

| ID | Point of failure | What is durable afterward |
|----|----|----|
| F1 | `routine.activate`'s own CAS `Update` fails (stale Version) | Nothing changed; Routine stays at its prior Status. No Schedule attempted. |
| F2 | Routine Status commit succeeds, its Event publish fails | Routine is durably Active (Store write committed before Event publish, matching the existing "commit survives Event failure" discipline every other Domain already uses); `ResponsibilityEventPublicationError`-shaped error returned, but Schedule creation is *never reached* in the current code path since it returns early via `finishDurableCommand`'s wrapped error. |
| F3 | Routine Active commit succeeds; `PlanScheduleCreation` preflight rejects (e.g., a stale duplicate ID) | Routine Active, no Schedule record exists at all. |
| F4 | Routine Active commit succeeds; the Schedule's own `registry.Create` write fails | Routine Active, no Schedule record (the atomic creator is all-or-nothing) — or, in the narrower case where the write itself succeeded but the *Ledger's own* `Finish` commit failed afterward, a Schedule record *does* exist as Pending even though the outer `schedule.create` Command reports failure. |
| F5 | Schedule persisted; the outer `schedule.create` Command's own Ledger `Finish` fails | Same as the F4 partial case: Schedule exists and is dispatchable; only the *reporting* of success is what failed. |
| F6 | Process crash between any of the above durable boundaries | Whatever was durably committed up to the crash point persists; nothing beyond it does. Every one of F1–F5's "what is durable" columns already describes exactly what a crash at that point leaves behind — there is no additional ambiguous state a crash introduces beyond what a synchronous failure at the same point already produces, because every write in this chain is already a single atomic Store operation or a single Ledger `Finish` call. |

The common shape across F3/F4/F5 (and, by the same reasoning, F6 landing inside any of them) is exactly the bug: **Routine Active, next occurrence absent, no durable signal**. F1 and F2 are not this bug — F1 changes nothing, and F2 is an orthogonal, already-accepted-elsewhere risk (Event publication failure) that must not be conflated with Schedule absence.

**Same failure window in post-occurrence continuation**, confirmed by re-reading `executeClaimedRoutinePlan`: after a dispatched occurrence's own Planning attempt (success or failure), the function unconditionally calls the same Schedule-creation logic to chain the next occurrence. Exactly the same F3/F4/F5 shape applies there — a chaining failure leaves an Active Routine with no future occurrence, indistinguishable from the activation case. Per this Checkpoint's own instruction not to fix activation while leaving dispatch continuation exposed, both call sites needed the same treatment.

## Decision

**Invariant** (v1, and the one this Checkpoint enforces): for every Active Routine, either (A) a future pending or dispatching Schedule targeting `routine.plan` for it exists, or (B) that absence is a Human-actionable, on-demand-detectable fact. "Active Routine + no Schedule + no way to notice" is never acceptable; this Checkpoint does not require (and does not build) an automatic background sweep — detectability is on-demand (read on request), matching every other read-side projection in this codebase.

**Existing-primitive audit** (Step 3), confirmed from source: Scheduler has no `Cancel`, and no recurrence/duplicate index beyond `Record.ScheduleID` and the Command Ledger's own `CommandID`. `internal/recovery` (`recovery-inspect`/`-plan`/`-apply`) is a Task/Deliverable/Review/Revision-specific residual-state mechanism (`DeliverableEvidence`, `ReviewEvidence`, `AuditEvidence`, ...) with no shape for Scheduler/Routine facts at all — extending it here would be a domain mismatch, not reuse. What *is* directly reusable: Schedule Store `Get`/`List` (read), `ExecuteScheduleCreation`'s own existing duplicate-ID/duplicate-target-Command blocking, and Command Ledger's existing "same CommandID replays, new CommandID genuinely retries" discipline.

**Selected model: E — deterministic occurrence reconciliation**, not a two-phase Routine status (Model C) or a reordered Schedule-first commit (Model B). Comparison:

| Model | Crash safety | Duplicate risk | No-op behavior | Diff size |
|---|---|---|---|---|
| A (current, unmodified) | Leaves the Continuity violation open | Low (protected by existing ID determinism) | N/A — no repair path | none |
| B — Schedule first, then Routine Active | Just moves the *same* window: a Schedule could exist for a Routine never marked Active | Low | N/A | Comparable, no net improvement |
| C — `inactive → activating → active` two-phase status | Requires a third Status value, a new transition, and a *separate* sweep to resolve stuck `activating` records back to a terminal state — the sweep problem is not actually solved by adding a phase | Unchanged | Still needs an explicit resolver | Largest — new Status, new transition rules, new stuck-state handling |
| D — current ordering + an explicit recovery marker on the Routine record | Solves detectability by duplicating Scheduler-owned state onto the Routine record | Unchanged | Needs the marker cleared correctly | Adds persisted state to Routine Core (explicitly discouraged, see Step 21/ADR-0063's own "no arbitrary metadata") |
| **E — deterministic reconciliation (selected)** | A missing occurrence is always re-derivable from the Routine's own already-persisted Trigger/Status; no new persisted state is needed to detect or repair it | Structurally bounded by Schedule ID determinism, not by Ledger replay alone (see below) | Reconciling an already-healthy Routine is a pure read, zero writes | Smallest: one new read function, one small write-idempotency change to an existing helper, one new explicit repair operation |

Model E was preferred because it needs no new Routine-record state (matching ADR-0063's own "no arbitrary metadata" discipline) and treats "the Routine's Trigger + current time" as the single source of truth for what *should* exist — reconciliation recomputes rather than resurrects, consistent with this repository's existing preference for detectable-and-idempotent recovery over rollback (recovery.go's own Task-level design follows the same shape: reconstruct from evidence, never undo a commit).

**`scheduleNextRoutineOccurrence` becomes idempotent by construction.** Before attempting `ExecuteScheduleCreation`, it now reads the Schedule Store directly for this occurrence's deterministic ID (`routineOccurrenceIdentity(record, after)`, factored out of the old inline derivation). If a non-terminal Schedule already exists there, it is returned as-is — no second creation attempt, no error. This one change is shared by all three callers: `ExecuteRoutineActivate`'s first occurrence, `executeClaimedRoutinePlan`'s post-occurrence chaining, and the new explicit `ExecuteRoutineReconcile` (Step 12's "common small reconciliation primitive," not a generic framework — one unexported helper, three callers).

**`ExecuteRoutineActivate`'s success semantics are unchanged in shape but now backed by a stronger guarantee**: it already returned success only when both the transition committed *and* Schedule creation succeeded (never a silent half-success — it already propagated `scheduleErr`). What changes is that a *retry* of the Schedule-creation half (via reactivation, or via the new `routine-reconcile`) is now genuinely idempotent against an already-existing occurrence, not merely protected by incidental Ledger-CommandID determinism.

**Deterministic identity, reused, not reinvented.** `routineOccurrenceIdentity` keeps the exact `ROUTINE-<RoutineID>-<dueAt>` / `routine-plan-<RoutineID>-<dueAt>` scheme ADR-0063 already established — no new hash scheme. The *outer* `schedule.create` Ledger Command's own CommandID, however, is no longer required to be perfectly deterministic: activation and chaining keep the original deterministic default (`"schedule-" + targetCommandID`), but `ExecuteRoutineReconcile` supplies its own operator-provided CommandID. This is necessary and deliberate: a deterministic CommandID means *replaying the same outer Command* (activation or chaining) always replays the same chaining outcome — including a stale cached failure. Only a genuinely new Command (a fresh, explicit `routine-reconcile` invocation) can un-stick that, exactly matching how every other Ledger-governed Command in this codebase already requires a new CommandID for a genuine retry. The read-check-first behavior is what keeps this safe: a fresh CommandID attempting to create a Schedule that already exists is intercepted before ever reaching `ExecuteScheduleCreation`, so it can never race into `PlanScheduleCreation`'s own "target_command_id_already_scheduled"/"schedule_id_already_exists" blocking as a confusing failure — it now surfaces as a clean, successful no-op.

**Deactivation is unchanged.** No Schedule cancellation was added (none existed to reuse, per ADR-0063's own decision, reconfirmed here). `ExecuteRoutinePlan`'s existing dispatch-time fresh-Status read remains the sole guard against a since-deactivated Routine's stale pending Schedule; `InspectRoutineScheduleHealth`, `ExecuteRoutineReconcile`, and `scheduleNextRoutineOccurrence` all treat an Inactive Routine as trivially healthy/out-of-scope — reconciliation never creates a Schedule for an Inactive Routine (`ErrRoutineNotActiveForReconciliation`), so it cannot race against or paper over deactivation.

**Reactivation regression (Step 10) is now more robustly closed.** Deactivating and reactivating before an already-created occurrence's due time previously avoided a duplicate only as an *incidental* consequence of deterministic Ledger-CommandID replay. It is now guaranteed directly by the Schedule-Store read-check, which does not depend on CommandID determinism at all — a more robust, intentional guarantee rather than a side effect.

**Recovery/reconciliation surface (Step 13): `routine-show` gains a read-only `schedule_healthy` field** (`InspectRoutineScheduleHealth`, a full Schedule-Store scan filtered to non-terminal `routine.plan` targets for this RoutineID — the same List-and-filter shape `PlanScheduleCreation`'s own duplicate check already uses, no new indexing). This was chosen over extending `recovery-inspect` (domain mismatch, see above) and over a heavier dedicated diagnostic surface — it is the smallest addition that makes the invariant's violation visible on demand, requiring no new UI.

**Manual repair (Step 14): a new `routine-reconcile` CLI operation / `process.ExecuteRoutineReconcile`.** Explicit, approval-gated (mirrors `routine-activate`/`-deactivate` exactly), requires an operator-supplied CommandID, and does nothing beyond what `scheduleNextRoutineOccurrence` already does for every other caller — reused verbatim, not a new repair mechanism. Rejects an Inactive Routine outright (reconciliation only restores the Active-Routine invariant). No hidden retry anywhere: this is invoked only by explicit Human (or future Attention Feed) action, never a background loop, never on a timer, never inside another Command's own error path.

**Event publication failure (Step 8) is untouched and not conflated with this fix.** `RoutineEventPublicationError` (F2) remains exactly what it was — the Store write already committed; only the Event delivery failed. `InspectRoutineScheduleHealth` never reads Events, only the Schedule Store, so it cannot be confused by an Event-publication failure that has nothing to do with Schedule absence.

**Attention Feed readiness (Step 21), without adding Attention state to Routine Core.** `InspectRoutineScheduleHealth`'s `false` result is exactly the durable fact "Routine requires recovery" a future Attention Feed could project read-only — it is already computed from existing Schedule Store + Routine Record state, with nothing new persisted anywhere. No Attention-specific field, table, or Event was added this Checkpoint.

## Alternatives considered and rejected

- **A generic `RoutineTransactionManager`/`AutomationRecoveryEngine`/Saga framework**: rejected outright per this Checkpoint's own governing principle — the fix is one read-check inside one existing helper plus one small explicit repair function, not a new transaction abstraction.
- **Rolling back the Routine's Active transition on Schedule-creation failure**: rejected — this repository has consistently preferred detectable, idempotent forward recovery over rollback of an already-committed Store write (the same reasoning ADR-0021's Command Ledger and `internal/recovery`'s own Task-residual-state design already follow); a rollback would also race against a concurrent read of the now-Active Routine.
- **Two-phase Routine Status (`activating`)**: rejected — trades one detection problem for a structurally identical one (a stuck `activating` record still needs its own sweep/resolver), for a larger diff.
- **A recovery marker persisted on the Routine record**: rejected — duplicates Scheduler-owned state into Routine Core, which ADR-0063 already deliberately avoided ("no arbitrary metadata"); the fact is already fully re-derivable on demand from existing Schedule Store state.
- **Hidden/background retry of failed Schedule creation**: rejected outright per this Checkpoint's explicit prohibition — all repair is either explicit (`routine-reconcile`) or a consequence of the Routine's own ordinary future lifecycle transitions (reactivation).
- **Extending `internal/recovery`**: rejected — its entire shape (Deliverable/Review/Revision/Audit evidence) is Task-execution-specific; bending it to cover Scheduler/Routine facts would be a worse fit than the small, purpose-built `InspectRoutineScheduleHealth`.

## Consequences

- `ExecuteRoutineActivate`, post-occurrence chaining inside `ExecuteRoutinePlan`, and the new `ExecuteRoutineReconcile` all share one idempotent, read-check-first `scheduleNextRoutineOccurrence` — the same failure window is closed identically wherever it occurs, with no duplicated logic.
- The "Active Routine + missing next occurrence" state remains reachable (a Schedule-creation failure can still happen) but is now always both on-demand detectable (`routine-show`'s `schedule_healthy`) and explicitly, safely repairable (`routine-reconcile`) without any risk of creating a duplicate Schedule for the same nominal occurrence.
- No existing Contract, Kernel registration, Scheduler one-shot semantics, Command Ledger behavior, Task lifecycle, Approval semantics, or Routine record schema changed. `git diff` is additive-only across `internal/process/routine_plan.go` (idempotency + two new exported functions), `cmd/workcairn/main.go` (one new operation, one additive `routine-show` field), and their tests.
- Automatic background reconciliation, Attention Feed projection, and Schedule cancellation on deactivate remain explicitly out of scope, deferred to future, separately-authorized Checkpoints.
