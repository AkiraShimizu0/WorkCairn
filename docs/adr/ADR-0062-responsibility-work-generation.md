# ADR-0062: Responsibility Work Generation

## Status

Accepted

## Context

ADR-0060 (Goal) and ADR-0061 (Responsibility) established `Goal → Responsibility` as real, persisted, standing company state, but both explicitly deferred connecting Responsibility to the Planning engine — "Responsibility → Work generation is explicitly out of scope" (ADR-0061). This ADR (PHASE U-3) makes that connection: a Human Operator can now ask "plan the work for this Responsibility right now," and the request is resolved into the existing, unmodified production Planning path (`process.GenerateCEOPlan` → `service.CEOPlanService` → `ceoplan.BuildPrompt`/`ParseIntent`/`NormalizeIntent`).

The central constraint carried into this Checkpoint: **no new Planning engine**. The value delivered here is that Responsibility context can now reach Planning, not that Planning itself changes. Company OS's three layers stay distinct — Responsibility is standing state ("what to continuously watch over"), Planning is a point-in-time proposal ("what work should be done right now"), Task is canonical execution state ("what is actually tracked"). Responsibility must never directly create a Task or execute a Workflow.

## Decision

**`process.GenerateResponsibilityPlan`** (`internal/process/responsibility_work.go`) resolves a Responsibility's standing context and hands off to the existing, unmodified `GenerateCEOPlan`. It is a plain function, not a new Kernel-registered Service and not a new Ledger-wrapped Command — mirroring `GenerateCEOPlan` itself, which is neither.

**Trigger is manual only, and requires an explicit Human instruction (Model B).** `ResponsibilityPlanInput.Instruction` is required and non-blank; a Responsibility's `Title` alone is never expanded into a work request. Responsibility supplies standing context (Title, linked Goals); the Human Operator's Instruction supplies what should actually be planned right now. This is enforced by rejecting a blank Instruction before any Vault or Provider access. There is no Scheduler, Event, or polling trigger — this Checkpoint wires the CLI/process path only.

**Context resolution is deterministic and reuses existing lookups.** `GenerateResponsibilityPlan` loads the Responsibility Record via the same `responsibilityStoreFor` helper `process/responsibility.go` already uses, resolves linked Goals via the same `goalStoreFor`/`goalScopeFrom` pair Responsibility Create already uses for GoalRef existence validation, and reads the current Binding (if any) via `store.GetBinding`. No new Store, Service, or Vault primitive was introduced.

**Inactive Responsibilities are rejected, not auto-activated.** A new sentinel, `ErrResponsibilityInactiveForPlanning`, is returned before any Goal resolution or Provider call. Activating first is a separate, already-existing Command (`responsibility-activate`) the caller must invoke explicitly.

**An unassigned Responsibility may still generate a Plan.** Binding is resolved as best-effort display/traceability context only — `GetBinding` returning `responsibility.ErrNotFound` (no Binding has ever been created) is not an error for Planning purposes; `BoundEmployeeID` is simply left empty. This was a deliberate investigation, not a default: nothing in `ceoplan`'s assignment resolution reads a Responsibility "owner" at all — Task assignment is resolved purely from each proposed step's `RequiredRole` against the Organization roster, independent of who (if anyone) holds the Responsibility. Gatekeeping Planning on Binding presence would have been an invented restriction with no existing Company OS principle behind it, and would conflate two different questions ("who is accountable for this area" vs. "who should this Task be assigned to").

**Responsibility owner is never a Task-assignment override.** `BoundEmployeeID` is carried on the result purely for traceability/display. It is never passed into `ceoplan`'s assignment resolver, and a Product-Manager-owned Responsibility's generated Backend Task is still assigned to a Backend Engineer by the same `RequiredRole` matching every other Plan uses — confirmed by test (`TestGenerateResponsibilityPlanContextReachesRequest`: an unassigned Responsibility still produces a correctly role-assigned Task).

**Achieved/Abandoned linked Goals are included as context, not filtered.** `composeResponsibilityPlanningRequest` includes every linked Goal's Title/Outcome/Status verbatim, regardless of Status — matching ADR-0060/ADR-0061's "no automatic cascade" decisions. No cascade or filtering was added.

**Planning input conversion is plain Go string concatenation, matching an existing precedent.** `composeResponsibilityPlanningRequest` builds the `Request` string `GenerateCEOPlan` has always accepted as a plain argument, following the exact shape `interaction.Record.PlanningRequest()` already established for combining a Human request with additional structured context (`Request + "\n\n確認済みCEO回答(JSON):\n" + encoded answers`). System/User Prompt construction remains entirely `ceoplan.BuildPrompt`'s responsibility; Responsibility business semantics (Title, GoalRefs, Status) never reach the Provider Adapter — only plain, sanitized text does, and the Provider Runner remains Provider-call-only.

**Traceability is a wrapper, not a `ceoplan.Plan` schema change.** `ResponsibilityPlanningResult` wraps the unmodified `service.CEOPlanResult` in a new outer struct carrying `ResponsibilityID`, `ResponsibilityTitle`, `Scope`, `ProjectName`, `GoalRefs`, and `BoundEmployeeID`. `ceoplan.Plan`'s own JSON schema, digest computation, and the existing `ExecuteCEOPlanApply`/Command Ledger payload shape are all untouched. Plan generation is inherently ephemeral/preview-only until a Human explicitly approves and applies it through the existing, unmodified Apply path — deeper traceability threaded *through* Apply (e.g. onto the created Project/Task records themselves) is deferred to a future Checkpoint once there is real usage evidence for what should be persisted there.

**No Command Ledger wrapping.** Confirmed by reading `CEOPlanGenerationInput` (`internal/process/ceo_plan.go`) directly: it carries no `CommandID` field, and `GenerateCEOPlan` is not claim-before-effect governed — Plan generation is a real-time, non-replayable Provider call, not a durable idempotent write (that distinction belongs to `ExecuteCEOPlanApply`, which *is* Ledger-governed). `GenerateResponsibilityPlan` follows the same precedent exactly, rather than inventing a dedicated "ResponsibilityWorkLedger."

**No new Event.** Confirmed by reading `service.CEOPlanService.Generate`/`GenerateCEOPlan`: neither publishes any Event today. Adding `responsibility.work_planned` would be inconsistent with the more general operation it wraps having never had one, so none was added. This may be revisited once Responsibility Work Generation has an Interaction/UX surface where an Event would actually be observed by something.

**No direct Task/Workflow/Schedule creation, verified by test.** `GenerateResponsibilityPlan` returns after Plan generation; it never calls `TaskService`, `WorkflowService`, or a Scheduler primitive. `TestGenerateResponsibilityPlanNeverTouchesTaskProjectOrLedger` confirms `プロジェクト/` gains zero entries and the Command Ledger directory's entry count is unchanged after a successful Plan generation.

**Approval boundary is unchanged and reused, not weakened.** `GenerateResponsibilityPlan` requires `approved == true` (checked before Instruction validation, before any Vault read) exactly like `ceo-plan-generate`'s CLI wiring checks `--approved` before calling `GenerateCEOPlan`. Plan *generation* approval and Plan *apply* approval remain two separate, already-existing gates — nothing here collapses them.

**The generated Plan is proven Apply-compatible with the existing path, unchanged.** `TestGenerateResponsibilityPlanFeedsExistingApplyPath` takes `GenerateResponsibilityPlan`'s own output `.Generation.Plan` and feeds it, unmodified, into `PlanCEOPlanApply`/`ExecuteCEOPlanApply` — the same functions `ceo-plan-apply-plan`/`ceo-plan-apply` already use — and confirms it produces real Tasks in a temporary Vault. This is integration evidence, not new wiring: `responsibility-plan`'s CLI output is a canonical `ceoplan.Plan` an Operator can pass to the existing `ceo-plan-apply` operation as-is.

**CLI surface**: one new operation, `responsibility-plan`, mirroring `ceo-plan-generate`'s dispatch shape exactly (`--approved` check before any environment/HTTP-client construction, `errors.As` extraction of `*service.CEOPlanError.Stage` on failure). New flags: `--instruction` (the required Human instruction) and reuse of the already-registered `--responsibility-id`, `--responsibility-scope`, `--project`, `--model`. Failure classification (`responsibilityPlanFailureResponse`) adds three Responsibility/Goal-context-specific codes (`RESPONSIBILITY_NOT_FOUND`, `RESPONSIBILITY_INACTIVE`, `GOAL_REF_NOT_FOUND`) and otherwise forwards `service.CEOPlanError`'s existing Stage taxonomy verbatim — no Provider error/output is ever exposed raw.

**No Interaction Session integration this Checkpoint.** The existing canonical CEO request → Plan → Approval UX lives in `interaction`/`interaction_workflow.go`. Wiring Responsibility Work Generation into that flow would require a non-trivial Interaction-session-shape decision (how a Responsibility-sourced request should present itself inside a Session) that has no existing usage evidence to design against yet. Per this Checkpoint's own speed-priority instruction, that integration is deferred to a future Company View/UX Checkpoint; the CLI/process path built here does not duplicate Interaction's Planning business logic — it calls the same `GenerateCEOPlan` Interaction itself would eventually call.

## Alternatives considered and rejected

- **Deriving the work request purely from the Responsibility's Title (Model A)**: rejected — a Title like "continuously improve onboarding" is standing context, not a work request; expanding it into Planning input without an explicit Human instruction would fabricate an unstated work request, exactly the kind of assumption-fabrication this session's Planning/Synthesis Quality work exists to catch.
- **Rejecting Planning for an unassigned Responsibility**: rejected after investigation — `ceoplan`'s assignment resolver never reads a Responsibility owner, so gatekeeping on Binding presence would be an invented restriction, not one implied by any existing Company OS principle. Binding stays best-effort display context.
- **Adding `ResponsibilityID`/`GoalRefs` directly onto `ceoplan.Plan`'s own schema**: rejected — would break a stable, digest-covered Contract already relied on by `ExecuteCEOPlanApply` and the Interaction flow, for traceability that a wrapper struct already satisfies at this Checkpoint's scope.
- **A Command Ledger-governed `ResponsibilityWorkLedger`**: rejected — Plan generation is not a durable idempotent write; wrapping it would contradict `GenerateCEOPlan`'s own established precedent and add governance machinery nothing here needs yet.
- **Publishing a new `responsibility.work_planned` Event**: rejected — the more general operation this wraps (`CEOPlanService.Generate`) has never published an Event; adding one here would be premature Event proliferation with no current subscriber.
- **Automatic Plan Apply immediately after generation**: rejected outright — Human approval must always be interposed between Plan generation and Plan Apply, per Constitution Article 5.
- **A large `WorkGenerationEngine`/`ResponsibilityPlannerRegistry`/generic Trigger framework**: rejected — this Checkpoint's entire scope is reusing one existing function with resolved context; no framework is justified by a single manual trigger.
- **Wiring into the Interaction Session flow this Checkpoint**: rejected for now — no existing usage evidence for how a Responsibility-sourced request should present inside a Session; deferred to a future UX Checkpoint rather than guessed at.

## Consequences

- `Goal → Responsibility → Planning` is now a real, working connection: a Human Operator can run `workcairn responsibility-plan --responsibility-id ... --instruction "..." --model ... --approved` and receive a canonical `ceoplan.Plan`, traceable back to its source Responsibility and linked Goals, that can be fed into the existing, unmodified `ceo-plan-apply` operation to produce real Tasks.
- No existing Contract, Kernel registration, `ceoplan.Plan` schema, Command Ledger behavior, Task lifecycle, or Approval semantics changed. `git diff` is additive-only across `internal/process/responsibility_work.go` (new), `cmd/workcairn/main.go` (new flag, new operation branch, new failure classifier), and their tests.
- Routine, Scheduler-triggered Responsibility Planning, Event-triggered Planning, automatic Task creation, Interaction Session integration, and Attention Feed surfacing all remain explicitly out of scope, deferred to future, separately-authorized Checkpoints once this connection has real usage evidence.
- Deeper traceability persisted *through* Plan Apply (e.g., a `ResponsibilityID` recorded on the created Project/Task themselves) is deferred — this Checkpoint's traceability lives only on the ephemeral generation-time result.
