# ADR-0067: Planning Placeholder Rejection

## Status

Accepted

## Context

Real Provider Planning Acceptance runs (Phase T-8, T-13) and the most recent Human Acceptance run (a request for a社内FAQページ作業計画, split into research/writing/confirmation) have repeatedly produced a canonical CEO Plan whose `Summary` — and, in the latest run, a `Task`'s own title/description — was nothing but the literal string `"placeholder"`. `docs/AgenticOSQualityFoundation.md` already recorded this as a known limitation when Planning Quality Foundation was closed "sufficient for now" in Phase T-13, on the reasoning that it did not block Company OS structural work. With Public Beta approaching, a recurring, semantically-empty Plan field reaching a Human Operator for approval is no longer acceptable to leave open.

This ADR covers only this one recurring defect. It is not a reopening of Planning Quality Foundation (Intent Coverage / Work Coverage / Dependency Reasoning / Unsupported Assumptions / Missing Information remain exactly as Phase T-10/T-12/T-13 left them), not a Provider Adapter or Model Router change, and not a general content-quality framework.

**Root cause, established from source, not guessed**: the entire chain — `BuildPrompt` → Provider call (Structured Output, schema-constrained) → `ceoplan.ParseIntent` → `ceoplan.NormalizeIntent` → `ceoplan.NormalizeCandidate` — performs only *structural* validation on `Summary`/Task `Title`/`Rationale`: non-empty (after trim), correct JSON type. Nothing anywhere rejects a non-empty but semantically-empty value. Confirmed explicitly:

- `ceoplan.BuildPrompt`'s System Prompt contains no literal "placeholder" and does not encourage it — its one embedded example is real, concrete content, with an explicit instruction not to copy it verbatim. Prompt-literal leakage (candidate A) is ruled out.
- `ceoplan.IntentJSONSchema`'s field descriptions said only "must be a non-empty string" / "must contain a non-whitespace character" (candidate B, a schema-example artifact, is also ruled out — there was no placeholder text in the schema either, just an insufficiently narrow constraint, structurally the same gap as the Go-side validation).
- `ceoplan.ParseIntent` rejects an empty `description`/`summary` but accepts any other non-empty string (candidate D — confirmed, the actual gap).
- `ceoplan.NormalizeIntent` copies `intent.Summary`/`step.Description` into the candidate Plan verbatim (`Summary: strings.TrimSpace(intent.Summary)`, `Title/Rationale: step.Description`) with no additional check — no fallback/default substitution exists for these two fields (unlike `Objective`/`ProjectName`, which already have deterministic ADR-0046 fallbacks for the *blank* case only). Candidate E (a fallback literally inserting "placeholder") is ruled out — there is no such fallback anywhere.
- No fixture, golden, or production doc contains the literal outside of one already-existing, deliberately-pinned real-evidence test fixture (`planningacceptance`'s `planT8RealRun`, T-8's actual saved output, used only to regression-test the quality *evaluator*'s scoring — never production-reachable). Candidate F (test-fixture pollution) is ruled out.

**Conclusion: root cause is C + D** — the Provider is free to (and, per repeated real evidence, sometimes does) emit the token "placeholder" as lazy-fill content, and no layer in the production pipeline has ever rejected it, because every existing check is presence/type validation, not content validation.

## Decision

**One narrow, evidence-backed content invariant, added at the single existing choke point every Plan already passes through.** `ceoplan.NormalizeCandidate` is called by all three ways a `Plan` can come into canonical existence in this codebase: `ParseRunnerOutput` (legacy direct-canonical Runner output), `NormalizeIntent` (the current Intent-based production generation path), and `ValidateApprovedPlan` (the Apply-time re-validation path, used for both the normal approved-Plan-apply flow and any externally/manually supplied `--plan-json`). Adding the check exactly once, here, means it applies to Plan *generation* and Plan *Apply* alike, and to Interaction (`interaction.plan.generate`), Responsibility Planning (`GenerateResponsibilityPlan`), and Routine dispatch (which calls `GenerateResponsibilityPlan`) alike — confirmed directly from source: `GenerateCEOPlan` is the only caller of `CEOPlanService.Generate`, and `internal/process/interaction.go` and `internal/process/responsibility_work.go` are its only two callers. No per-path validator was written or copy-pasted.

**Definition, deliberately narrow**: `isPlaceholderValue` matches only the exact literal token `"placeholder"` — trimmed of whitespace and one layer of common wrapping punctuation (`<>`, `[]`, `{}`, quotes), case-folded. A sentence that merely *contains* the word ("placeholder text should be replaced") is never rejected. This is the one token real evidence has actually shown; no generic banned-word list (`TBD`, `dummy`, `N/A`, etc.) was added without evidence, and no substring/fuzzy match was implemented — an exact match only, matching the Checkpoint's own explicit caution against over-broad rejection.

**Fields covered**: Plan `Summary`, Task `Title`, Task `Rationale` — the three fields real evidence has actually shown affected. `Objective`, `ProjectName`, and `CEOQuestions` were deliberately left uncovered: no repo evidence shows them affected, and `Objective`/`ProjectName` already have their own ADR-0046 blank-value fallback behavior that a content check would need to reason about separately without evidence to justify doing so.

**Failure classification reuses the existing taxonomy additively.** A new `ceoplan.ParseFailurePlaceholderValue` constant was added to the existing `ParseFailureReason` enum (the same enum `ParseFailureInvalidTaskShape`/`ParseFailureMissingRequiredField`/etc. already live in) and returned via the existing `*ceoplan.ParseError` type — no new Error type. Because it originates from `NormalizeCandidate`, `service.CEOPlanService.Generate`'s existing Stage-classification logic (`errors.As(err, &normalizationErr)` distinguishes `CEOPlanNormalizationStage` from the default `CEOPlanParserStage`) classifies it as `CEOPlanParserStage` automatically, identically to how a bad project name or invalid task shape is already classified — zero changes were needed to `CEOPlanService.Generate`, `GenerateCEOPlan`, or any CLI/HTTP error-mapping code. The safe field path (`"summary"`, `"proposed_tasks[1].title"`, etc.) is carried in the wrapped error text, following the exact same pattern every other `NormalizeCandidate` failure already uses — no raw Provider content is ever included.

**No hidden retry, no substitution.** Placeholder detection returns a typed failure; it never triggers a second Provider call, never auto-generates a replacement Task name, never copies `Objective` into `Summary`, and never substitutes a blank/"未設定" value. The Human Operator's only path forward is an explicit new Planning request (a new Command/Session step), exactly as for any other Planning failure.

**Minimal, additive Prompt/schema improvement, not the fix itself.** Since the root cause is "the Provider is allowed to do this," not "the Prompt tells it to," this Checkpoint added exactly one short instruction line to `BuildPrompt`'s System Prompt ("summaryやdescriptionに「placeholder」「TBD」などの仮の値を出力しないでください") and extended the existing JSON-Schema field descriptions for `summary`/step `description` (the "one canonical place the full wording lives," per the existing precedent already established for the "non-empty" rule) to also name the placeholder token. This is defense-in-depth to reduce *recurrence frequency*; it is explicitly not relied on as the actual guarantee — the runtime `NormalizeCandidate` check is.

**Planning Quality Evaluator untouched.** `internal/planningacceptance`'s five-axis Evaluator (Intent Coverage, Work Coverage, Dependency Reasoning, Unsupported Assumptions, Missing Information) gained no placeholder-specific axis or scoring rule — this is a *runtime production contract* concern, not a quality-scoring concern, and the two must not be conflated (the Checkpoint's own explicit instruction). The T-8 real-evidence fixture (`planT8RealRun`, which contains a pinned `Summary: "placeholder"`) is untouched: it already scores poorly via the Evaluator's other axes, and it exists specifically to regression-test that scoring, not to exercise this new runtime guard.

## Alternatives considered and rejected

- **A generic banned-word/content-quality framework**: rejected outright per this Checkpoint's own governing principle — one evidence-backed exact-match token, not a rules engine.
- **Adding the check to `ParseIntent`/`IntentParseError` instead of `NormalizeCandidate`**: rejected — `ParseIntent` is explicitly documented as performing only structural/presence validation and deferring all business validation downstream; adding a content rule there would also miss the `ValidateApprovedPlan`/Apply-time path entirely, since that path never goes through `ParseIntent` at all.
- **A separate validator duplicated into `NormalizeIntent`, `CEOPlanService.Generate`, and each of the Interaction/Responsibility/Routine call sites**: rejected — `NormalizeCandidate` is the one function all of them already funnel through; duplicating the check anywhere else would be exactly the copy-paste the Checkpoint's own instructions (Steps 17/18) forbid.
- **Auto-substitution (regenerate the Summary from Objective, replace with "未設定", retry the Provider)**: rejected outright — explicitly forbidden by this Checkpoint; a rejected Plan must stay rejected, visibly, until a Human explicitly asks again.
- **A fuzzy/substring placeholder ban**: rejected — real evidence shows only the exact bare token; a substring ban risks false-rejecting legitimate content that happens to mention the word "placeholder" in a real sentence.
- **Extending the check to `Objective`/`ProjectName`/`CEOQuestions`**: rejected for v1 — no repo evidence either is affected; extending without evidence would be exactly the guessing this Checkpoint's instructions prohibited.

## Consequences

- A Plan whose Summary or any Task's Title/Rationale is exactly the placeholder token is rejected as `ParseFailurePlaceholderValue` (surfaced as `CEOPlanParserStage`) at generation time — before it ever reaches a Human Operator for approval — across every Planning path (Interaction, manual Responsibility Planning, Routine dispatch) and, redundantly, at Plan Apply time too, all through one shared check.
- No existing Contract, Kernel registration, Provider Adapter, Approval semantics, or Planning Quality Evaluator changed. `git diff` is additive-only across `internal/ceoplan/plan.go` (one new `ParseFailureReason` value, one new unexported helper, three call sites), `internal/ceoplan/prompt.go`/`schema.go` (one instruction line, two extended field descriptions), and their tests.
- This closes the specific, repeatedly-observed "placeholder" defect. It does not claim to have solved Planning content quality generally — other forms of low-effort or generic output remain a Planning Quality Evaluator concern, not a runtime-rejection concern, and are explicitly out of scope here.
